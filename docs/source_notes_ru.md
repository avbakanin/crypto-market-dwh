# Источник: Binance Spot API — klines

- Endpoint: `GET https://api.binance.com/api/v3/klines`
- Зеркало для рыночных данных: `https://data-api.binance.vision`
- Параметры: `symbol`, `interval`, `startTime`, `endTime`, `limit` (по умолчанию 500, максимум 1000)
- Документация: https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints

## Поля (массив из 12 элементов)

| # | Поле | Тип в ответе | Пример (BTCUSDT, 2026-11-19 15:00 UTC) |
|---|------|--------------|------------------------------------------|
| 0 | open_time (мс, UTC) | int | 1795100400000 |
| 1 | open | string | "63558.00000000" |
| 2 | high | string | "63916.01000000" |
| 3 | low | string | "62780.07000000" |
| 4 | close | string | "63103.30000000" |
| 5 | volume (BTC) | string | "1213.38723000" |
| 6 | close_time (мс, UTC) | int | 1795103999999 |
| 7 | quote_volume (USDT) | string | "76724531.04007310" |
| 8 | trades_count | int | 206590 |
| 9 | taker_buy_base_volume | string | "631.83302000" |
| 10 | taker_buy_quote_volume | string | "39946372.67800280" |
| 11 | ignore | string | "0" |

## Наблюдения для Data Quality

1. **Ключ свечи — open_time.** Интервал `[open_time, open_time + 1h − 1ms]`; следующая свеча начинается с `close_time + 1 мс`.
2. **Последняя свеча может быть не закрыта.** 2026-11-19 в 17:22 UTC свеча 17:00 имела volume 509 BTC против ~1200 у закрытых. Правило: загружать только свечи с `close_time < now`.
3. **Цены и объёмы приходят строками**, чтобы не терять точность (quote_volume — до 16 значащих цифр). Хранить как `NUMBER(38, 8)`, не конвертировать во float.
4. **Время в Unix epoch, миллисекунды, UTC.** При конвертации в Python всегда указывать `tz=timezone.utc`.
5. **Объём выборки:** год часовых свечей ≈ 8760 строк, это минимум 9 запросов по 1000 на одну монету.
6. **Опечатка в тикере может молча вернуть другой инструмент.** `BTCUSD` (вместо `BTCUSDT`) отдаёт валидные данные с похожей ценой (+0.2%), но объёмом в ~16 000 раз меньше. Защита: фиксированный список тикеров (`dim_symbol` + dbt-тест `relationships`) и минимальный порог ликвидности.

## Наблюдения при отборе монет (whitelist)

Скрипт: `ingestion/select_symbols.py` → `config/symbols.csv` (будущий источник для `dim_symbol`).

7. **Неполная история у новых листингов.** У монеты, залистенной 3 месяца назад, ~2 200 часовых свечей вместо ~8 760 за год; при сравнении монет это выглядит как разрывы. → Правило: `first_candle_date` не позже чем 365 дней назад.
8. **Тикер ≠ актив.** Переименования разрывают историю между символами: LUNA → LUNC после краха Terra (май 2022), поэтому `LUNCUSDT` начинается с 2022-09-09. `first_candle_date` — дата листинга тикера, а не актива. → Не склеивать символы по имени base asset без таблицы соответствий.
9. **Не-крипто инструменты на споте.** Стейблкоины (новые появляются постоянно, например RWUSD в октябре 2026), токены на золото (PAXG, XAUT), токенизированные акции/ETF (NVDAB, QQQB, MSTRB, …). → Явный список исключений + правило по данным: диапазон close за 30 дней внутри [0.98, 1.02] ⇒ пег к USD, исключаем. Открытый вопрос: токенизированные акции сейчас отсекаются только правилом истории.
10. **Оборот за 24h — шумная метрика ликвидности.** MMTUSDT: 52.6M за 24h против 2.3M в среднем за 30 дней (×22); LUNCUSDT ×9; SKYUSDT ×8. Снимок за один день дал 3 ложных срабатывания из 24. → Правило: средний дневной оборот за 30 дней ≥ 10M USDT.
11. **Whitelist — это снимок.** Обороты меняются ежедневно, перезапуск скрипта меняет список. → `config/symbols.csv` коммитится в git и пересобирается только осознанно; `selected_at_utc` фиксирует момент.

## Наблюдения о поведении API

12. **Семантика ошибок.** Ошибки приходят с JSON-телом `{"code": ..., "msg": ...}`, например `HTTP 400 {"code":-1121,"msg":"Invalid symbol."}`. 4xx — наша ошибка, не ретраим. 429 — rate limit, может содержать `Retry-After` (секунды). 418 — бан IP после игнорирования 429, не ретраим (повторы продлевают бан). 5xx — временная ошибка, ретраим с экспоненциальным backoff. → Реализовано в `ingestion/clients/binance.py`.
13. **Ожидаемое число строк — 8 759, а не 8 760.** `startTime` не выровнен по часу, Binance отдаёт свечи с `open_time >= startTime`, поэтому первая свеча — следующий полный час; текущий час отбрасывается как незакрытый. Проверено на всех 23 монетах: 8 759 строк, 0 дублей, 0 разрывов (as of 2026-11-19 18:31 UTC). → Проверка количества строк должна ожидать 8 759 для окна в 365 дней от единого as-of момента.
14. **Без `startTime` klines отдаёт последние `limit` свечей, и последняя из них ещё не закрыта.** Проверено 2026-11-19 20:11 UTC: `BTCUSDT 1d limit=3` вернул два закрытых дня и сегодняшнюю свечу с `close_time > now`. С `startTime=0, limit=1` API отдаёт самую первую свечу (BTCUSDT: 2017-08-17), то есть дату листинга. → `select_symbols.get_daily_stats` запрашивает `limit = days + 1` и отбрасывает последнюю свечу (`[:-1]`). Здесь `[:-1]` правилен, в отличие от пагинации по `startTime` (п. 2), где на полных страницах все свечи закрыты. Оговорка: если торги остановлены, последняя свеча может быть уже закрыта, и `[:-1]` выбросит один нормальный день.

## Наблюдения о платформе: Snowflake

Trial-аккаунт создан 2026-11-20 (edition Standard, `AWS_US_EAST_2`). Скрипт настройки: `snowflake/setup.sql`.

15. **Выбранная роль — не единственная действующая.** У пользователей по умолчанию `DEFAULT_SECONDARY_ROLES = ('ALL')`, поэтому права дают все роли, выданные пользователю. Под `CRYPTO_DWH_ROLE`, у которой нет `OWNERSHIP` на схемы, `DROP SCHEMA CRYPTO_DWH.RAW` прошёл; в `ACCOUNT_USAGE.QUERY_HISTORY` у этого оператора `secondary_role_stats = {"roleCount":4,...}`. После `USE SECONDARY ROLES NONE` он падает с «Insufficient privileges ... must have OWNERSHIP». Snowsight сам выполняет `USE SECONDARY ROLES ALL` в своих сессиях; у вкладки одна сессия на все запуски, и `USE ROLE` secondary roles не сбрасывает. → Наименьшие привилегии обеспечиваются набором ролей у пользователя: загрузчику — отдельный service-пользователь только с проектной ролью. Негативные тесты прав запускать с выключенными secondary roles, иначе проверяется пользователь, а не роль.
16. **«Does not exist or not authorized» означает любое из двух.** `CREATE TABLE` в удалённой схеме и `USE WAREHOUSE` без `USAGE` дают ошибку одного вида: Snowflake не раскрывает роли, которая не видит объект, существует ли он. → При отладке сначала проверить существование объекта под админской ролью, потом подозревать гранты (и наоборот).
17. **Новый trial-аккаунт приходит с warehouse, которые простаивают по 5 минут.** Форма регистрации назначила облачный регион и edition, не спрашивая. Snowflake заранее создал `COMPUTE_WH` (default пользователя) и `SNOWFLAKE_LEARNING_WH` с `AUTO_SUSPEND = 300`, плюс `SYSTEM$STREAMLIT_NOTEBOOK_WH` с 60; все X-Small, Gen2 (`STANDARD_GEN_2`), владелец `ACCOUNTADMIN`. Gen2 — default для новых warehouse и на AWS стоит ×1.35 кредитов Gen1; `STATEMENT_TIMEOUT_IN_SECONDS` по умолчанию — 2 суток. → `setup.sql` создаёт проектный warehouse с явным `GENERATION = '1'`, `AUTO_SUSPEND = 60`, таймаутом 600 с и применяет те же лимиты простоя и таймаута к созданным заранее warehouse.
18. **Операции с метаданными не будят warehouse; `updated_on` — не журнал изменений.** `USE`, `SHOW`, `CREATE`/`DROP TABLE` и context-функции выполнялись при suspended `CRYPTO_WH` (`resumed_on` остался на последнем реальном запросе). `updated_on` менялся при холостом `ALTER ... SET` с теми же значениями и при каждом пробуждении. → Считать кредиты по метрингу warehouse, а не по числу запросов; дрейф конфигурации отслеживать сравнением свойств с `setup.sql`, а не по `updated_on`.
