# Источник: Binance Spot API — klines

- Endpoint: `GET https://api.binance.com/api/v3/klines`
- Зеркало для рыночных данных: `https://data-api.binance.vision`
- Параметры: `symbol`, `interval`, `startTime`, `endTime`, `limit` (по умолчанию 500, максимум 1000)
- Документация: https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints

## Поля (массив из 12 элементов)

| # | Поле | Тип в ответе | Пример (BTCUSDT, 2026-11-19 15:00 UTC) |
|---|------|--------------|------------------------------------------|
| 0 | open_time (мс, UTC) | int | 1795100400000 |
| 1 | open | string | "63558.00000000" |
| 2 | high | string | "63916.01000000" |
| 3 | low | string | "62780.07000000" |
| 4 | close | string | "63103.30000000" |
| 5 | volume (BTC) | string | "1213.38723000" |
| 6 | close_time (мс, UTC) | int | 1795103999999 |
| 7 | quote_volume (USDT) | string | "76724531.04007310" |
| 8 | trades_count | int | 206590 |
| 9 | taker_buy_base_volume | string | "631.83302000" |
| 10 | taker_buy_quote_volume | string | "39946372.67800280" |
| 11 | ignore | string | "0" |

## Наблюдения для Data Quality

1. **Ключ свечи — open_time.** Интервал `[open_time, open_time + 1h − 1ms]`; следующая свеча начинается с `close_time + 1 мс`.
2. **Последняя свеча может быть не закрыта.** 2026-11-19 в 17:22 UTC свеча 17:00 имела volume 509 BTC против ~1200 у закрытых. Правило: загружать только свечи с `close_time < now`.
3. **Цены и объёмы приходят строками**, чтобы не терять точность (quote_volume — до 16 значащих цифр). Хранить как `NUMBER(38, 8)`, не конвертировать во float.
4. **Время в Unix epoch, миллисекунды, UTC.** При конвертации в Python всегда указывать `tz=timezone.utc`.
5. **Объём выборки:** год часовых свечей ≈ 8760 строк, это минимум 9 запросов по 1000 на одну монету.
6. **Опечатка в тикере может молча вернуть другой инструмент.** `BTCUSD` (вместо `BTCUSDT`) отдаёт валидные данные с похожей ценой (+0.2%), но объёмом в ~16 000 раз меньше. Защита: фиксированный список тикеров (`dim_symbol` + dbt-тест `relationships`) и минимальный порог ликвидности.

## Наблюдения при отборе монет (whitelist)

Скрипт: `ingestion/select_symbols.py` → `config/symbols.csv` (будущий источник для `dim_symbol`).

7. **Неполная история у новых листингов.** У монеты, залистенной 3 месяца назад, ~2 200 часовых свечей вместо ~8 760 за год; при сравнении монет это выглядит как разрывы. → Правило: `first_candle_date` не позже чем 365 дней назад.
8. **Тикер ≠ актив.** Переименования разрывают историю между символами: LUNA → LUNC после краха Terra (май 2022), поэтому `LUNCUSDT` начинается с 2022-09-09. `first_candle_date` — дата листинга тикера, а не актива. → Не склеивать символы по имени base asset без таблицы соответствий.
9. **Не-крипто инструменты на споте.** Стейблкоины (новые появляются постоянно, например RWUSD в октябре 2026), токены на золото (PAXG, XAUT), токенизированные акции/ETF (NVDAB, QQQB, MSTRB, …). → Явный список исключений + правило по данным: диапазон close за 30 дней внутри [0.98, 1.02] ⇒ пег к USD, исключаем. Открытый вопрос: токенизированные акции сейчас отсекаются только правилом истории.
10. **Оборот за 24h — шумная метрика ликвидности.** MMTUSDT: 52.6M за 24h против 2.3M в среднем за 30 дней (×22); LUNCUSDT ×9; SKYUSDT ×8. Снимок за один день дал 3 ложных срабатывания из 24. → Правило: средний дневной оборот за 30 дней ≥ 10M USDT.
11. **Whitelist — это снимок.** Обороты меняются ежедневно, перезапуск скрипта меняет список. → `config/symbols.csv` коммитится в git и пересобирается только осознанно; `selected_at_utc` фиксирует момент.

## Наблюдения о поведении API

12. **Семантика ошибок.** Ошибки приходят с JSON-телом `{"code": ..., "msg": ...}`, например `HTTP 400 {"code":-1121,"msg":"Invalid symbol."}`. 4xx — наша ошибка, не ретраим. 429 — rate limit, может содержать `Retry-After` (секунды). 418 — бан IP после игнорирования 429, не ретраим (повторы продлевают бан). 5xx — временная ошибка, ретраим с экспоненциальным backoff. → Реализовано в `ingestion/clients/binance.py`.
13. **Ожидаемое число строк — 8 759, а не 8 760.** `startTime` не выровнен по часу, Binance отдаёт свечи с `open_time >= startTime`, поэтому первая свеча — следующий полный час; текущий час отбрасывается как незакрытый. Проверено на всех 23 монетах: 8 759 строк, 0 дублей, 0 разрывов (as of 2026-11-19 18:31 UTC). Прямое подтверждение 2026-11-20: для as-of 19:40:05 UTC (`startTime` = 2025-11-20 19:40:05) первая свеча в RAW открывается в 20:00:00, а не в 19:00 (свеча, содержащая `startTime`). → Проверка количества строк должна ожидать 8 759 для окна в 365 дней от единого as-of момента.
14. **Без `startTime` klines отдаёт последние `limit` свечей, и последняя из них ещё не закрыта.** Проверено 2026-11-19 20:11 UTC: `BTCUSDT 1d limit=3` вернул два закрытых дня и сегодняшнюю свечу с `close_time > now`. С `startTime=0, limit=1` API отдаёт самую первую свечу (BTCUSDT: 2017-08-17), то есть дату листинга. → `select_symbols.get_daily_stats` запрашивает `limit = days + 1` и отбрасывает последнюю свечу (`[:-1]`). Здесь `[:-1]` правилен, в отличие от пагинации по `startTime` (п. 2), где на полных страницах все свечи закрыты. Оговорка: если торги остановлены, последняя свеча может быть уже закрыта, и `[:-1]` выбросит один нормальный день.
26. **Локальные часы — не часы Binance.** Пять вызовов `GET /api/v3/time` 2026-11-20: сервер впереди локальных часов на 1.34 с (round trip ~250 мс). `drop_unclosed` и `batch_id` берут локальное время: если локальные часы *спешат*, свеча считается закрытой раньше настоящего закрытия на величину расхождения, пока её объём ещё меняется. Здесь расхождение в безопасную сторону. → Инкрементальный extract перечитывает последнюю выгруженную свечу (`OVERLAP_CANDLES = 1`): взятая слишком рано свеча придёт в финальном виде следующим запуском, а staging возьмёт версию из самого свежего батча. Время сервера как as-of не используем (лишний запрос); вернуться, если расхождение окажется в опасную сторону.
27. **Закрытые свечи не меняются.** Последние 48 закрытых часовых свечей батча `20261120T194005Z` (выгружен через 40 минут после закрытия последней) сравнили с живым API примерно через час: 1 104 свечи, 0 расхождений. После первой инкрементальной загрузки 23 свечи стыка, попавшие в оба батча, в RAW совпали байт в байт (`COUNT(DISTINCT TO_JSON(payload)) = 1` на свечу). → HWM-инкремента достаточно, CDC не нужен; перекрытие в 1 свечу — дешёвая страховка, а тот же запрос к RAW — детектор правок, который стоит гонять и дальше.
28. **Границы `startTime` и цена запросов.** `startTime`, равный `open_time` свечи, возвращает эту свечу первой (включительно); `startTime` в будущем → `[]`; `startTime` на текущем часе → только незакрытая свеча. Вес `GET /api/v3/klines` — 2 при любом `limit`; `exchangeInfo` сообщает лимит `REQUEST_WEIGHT` 6 000 в минуту, заголовок `X-MBX-USED-WEIGHT-1M` — израсходованный вес (2026-11-20). → Инкремент начинается ровно с HWM, чтобы перечитать эту свечу; символ, у которого HWM уже равен последней закрытой свече, пропускается без запроса — запуск без нового стоит 0 веса вместо 46 (23 × 2).

## Наблюдения о фьючерсном API Binance (USD-M)

Эндпоинты `https://fapi.binance.com` для funding rate и open interest; живые пробы 2026-11-20/21 по 23 монетам whitelist.

30. **Доступ и лимиты.** `fapi.binance.com` отвечает из Черногории без VPN; локальные часы отставали от фьючерсного сервера на 1.77 с (безопасное направление, как в п. 26). `exchangeInfo` сообщает лимит `REQUEST_WEIGHT` 2 400 в минуту (спот — 6 000). История funding делит отдельный лимит 500 запросов за 5 минут с `fundingInfo`; история open interest — 1 000 запросов за 5 минут. Эти два эндпоинта не возвращают заголовок `X-MBX-USED-WEIGHT`, расход по ответу не узнать. → Первый прогон — около 50 запросов funding и 46 open interest, ежечасный — около 23 запросов open interest и ни одного funding между расчётами; extract делает паузу 0.2 с между страницами.
31. **Спот-символ ≠ символ фьючерса; подстрока врёт.** У 22 из 23 монет USD-M perpetual с тем же символом; `PEPEUSDT` соответствует `1000PEPEUSDT` (`baseAsset` `1000PEPE`, цена за 1 000 монет). Поиск по подстроке символа находит чужие контракты: `BTCDOMUSDT` (индекс доминации BTC), `PUMPBTCUSDT` (другая монета, статус `SETTLING`), `ETHFIUSDT`, `ETHWUSDT`. Квартальные контракты имеют тот же `baseAsset` (`BTCUSDT_261225`), а `contractType` `TRADIFI_PERPETUAL` помечает токенизированные акции (`OPENAIUSDT`, `UNITREEUSDT`) — явный признак, которого нет в спотовом `exchangeInfo` (п. 9). → `map_perpetuals` сравнивает `baseAsset` (с префиксом `1000`, `1000000` или `1M` или без), `contractType = PERPETUAL`, `status = TRADING`, котировку USDT и хранит множитель в `config/perpetuals.csv`; два кандидата на одну монету останавливают сопоставление.
32. **История funding: включительный `startTime`, первые `limit`, а `startTime=0` значит «не передан».** `startTime`, равный `fundingTime` записи, возвращает её первой, с точностью до миллисекунды; при диапазоне шире `limit` (максимум 1 000) приходят первые `limit` записей по возрастанию; `startTime` в будущем → `[]`. `startTime=0` считается отсутствующим и возвращает самые свежие записи, а не самые ранние (у спотовых klines — дату листинга, п. 14). История BTCUSDT начинается 2019-09-10; у старых записей `markPrice` — `""` (пустая строка), у записей последнего года значение есть; `rateType` — `Regular` (документация оставляет `Special` для дивидендов по акциям). → Пагинация вперёд от последнего `fundingTime + 1`; клиент отвергает `start_time <= 0`; staging должен считать пустой `markPrice` NULL, а не кастовать его.
33. **`fundingTime` приходит через несколько миллисекунд после часа.** За год расчётов BTCUSDT 461 из 1 000 ровно на часе, остальные на 1–26 мс позже (`00:00:00.007`). → Ключ сетки — час (`fundingTime // 1 ч`): проверки дублей и разрывов в extract, подсчёт дублей в RAW загрузчиком (`FLOOR(fundingTime / 3600000)`) и staging используют один ключ.
34. **Интервал funding разный у контрактов и меняется со временем.** 19 из 23 контрактов рассчитываются каждые 8 ч, ENA, PUMP, TAO и ASTER — каждые 4 ч (сетка от 00:00 UTC). `fundingInfo` перечисляет только контракты с изменённым cap, floor или интервалом (833 из 956); у `GTCUSDT` там сейчас 4 ч, а в июне 2026 расчёт шёл каждые 8 ч. Истории интервалов API не отдаёт. → Extract берёт текущий интервал (8 ч, если контракта нет в списке) и записывает его по файлу (`interval_hours`); `expected` — оценка, поэтому расхождение — DQ-предупреждение, а не стоп.
35. **Платформа пропускает расчёты.** Расчёта 2026-06-24 04:00 нет у 20 из 21 проверенного контракта, которые в тот день рассчитывались каждые 4 ч (ENA, PUMP, TAO, ASTER, LPTUSDT, KERNELUSDT и другие); есть только у IRYSUSDT. У 8-часовых контрактов в этот час расчёта нет по сетке. Поэтому первая годовая выгрузка показывает у четырёх 4-часовых контрактов `rows=2189, expected=2190, gaps=1`. → Реальная дыра источника, пойманная DQ-проверкой: сообщить, пометить в staging, не интерполировать.
36. **История open interest — около месяца, а более старое время — ошибка.** `openInterestHist` отдаёт скользящие 744 часовые точки (~31 день); `startTime` или `endTime` старше — `HTTP 400 {"code":-1130,"msg":"parameter 'startTime' is invalid."}`, а не пустой ответ (4xx не повторяется). В документации максимум `limit` — 500, но 501 и 1 000 принимаются (1 000 вернул все 744 точки). Метки ровно на часе; по документации период без сделок точки не имеет. → RAW — единственная копия open interest старше месяца, поэтому extract нужно запускать минимум раз в 30 дней; он запрашивает не больше 30 дней (день запаса от скользящей границы), точки, выпавшие из окна, отчитывает как `lost`, `limit` держит на документированных 500.
37. **Open interest листается в обратную сторону: ПОСЛЕДНИЕ `limit` точек.** При одном `startTime` или при `startTime` и `endTime`, охватывающих больше `limit` точек, приходят самые новые `limit` точек диапазона; klines и funding отдают самые старые. Пагинация вперёд по `startTime`, как у свечей, вернула бы новейшие 500 из 720 точек и молча потеряла первые 220. → Страницы — явные окна не шире 500 часов (`startTime` и `endTime = startTime + 499 ч`): окно не шире `limit` приходит целиком. Два окна дают 720 точек за 30 дней без дублей.
38. **Точка open interest T публикуется примерно через минуту после T и не меняется.** При опросе около 22:00 UTC 2026-11-20 точка 22:00 появилась через 61–76 с после начала часа; она и три предыдущие точки сохранили значения в следующие 7 и 20 минут. Документация описывает `timestamp` как конец периода. → Точка ожидается через 5 минут после своего времени (`PUBLISH_LAG_MS`), иначе запуск в начале часа выдал бы ложное «нет новых точек»; отметки уровня достаточно, перекрытие в одну точку доказывает стык. Задержка публикации funding ещё не измерена; принят тот же лаг 5 минут.
39. **Funding большую часть времени равен процентной ставке: повторяющееся значение — формула, а не зависшие данные.** FAQ Binance (обновлён 2026-03-06): `F = [P + clamp(I − P, 0.05%, −0.05%)] / (8 / N)`, процентная ставка `I` = 0.01 % за 8 ч для большинства символов; пока индекс премии между −0.04 % и 0.06 %, `F` равен `I`. В RAW (2025-11-21 — 2026-11-21) максимум ставки ровно `0.00010000` у 12 из 19 восьмичасовых контрактов и `0.00005000` (0.01 % / (8 / 4)) у 2 из 4 четырёхчасовых; минимумы уходят далеко вниз (INJUSDT −0.01183133, TAOUSDT −0.00359598). Все ставки — JSON-строки (`VARCHAR` в `VARIANT`) и точно приводятся к `NUMBER(38, 8)`. → DQ-проверка «значение не менялось N периодов» сработала бы на здоровых данных funding; сравнивать funding с `I / (8 / interval_hours)`, а не с прошлым значением, и помнить, что у 4-часовых контрактов ставка за 4 ч.

## Наблюдения о платформе: Snowflake

Trial-аккаунт создан 2026-11-20 (edition Standard, `AWS_US_EAST_2`). Скрипт настройки: `snowflake/setup.sql`.

15. **Выбранная роль — не единственная действующая.** У пользователей по умолчанию `DEFAULT_SECONDARY_ROLES = ('ALL')`, поэтому права дают все роли, выданные пользователю. Под `CRYPTO_DWH_ROLE`, у которой нет `OWNERSHIP` на схемы, `DROP SCHEMA CRYPTO_DWH.RAW` прошёл; в `ACCOUNT_USAGE.QUERY_HISTORY` у этого оператора `secondary_role_stats = {"roleCount":4,...}`. После `USE SECONDARY ROLES NONE` он падает с «Insufficient privileges ... must have OWNERSHIP». Snowsight сам выполняет `USE SECONDARY ROLES ALL` в своих сессиях; у вкладки одна сессия на все запуски, и `USE ROLE` secondary roles не сбрасывает. → Наименьшие привилегии обеспечиваются набором ролей у пользователя: загрузчику — отдельный service-пользователь только с проектной ролью. Негативные тесты прав запускать с выключенными secondary roles, иначе проверяется пользователь, а не роль.
16. **«Does not exist or not authorized» означает любое из двух.** `CREATE TABLE` в удалённой схеме и `USE WAREHOUSE` без `USAGE` дают ошибку одного вида: Snowflake не раскрывает роли, которая не видит объект, существует ли он. → При отладке сначала проверить существование объекта под админской ролью, потом подозревать гранты (и наоборот).
17. **Новый trial-аккаунт приходит с warehouse, которые простаивают по 5 минут.** Форма регистрации назначила облачный регион и edition, не спрашивая. Snowflake заранее создал `COMPUTE_WH` (default пользователя) и `SNOWFLAKE_LEARNING_WH` с `AUTO_SUSPEND = 300`, плюс `SYSTEM$STREAMLIT_NOTEBOOK_WH` с 60; все X-Small, Gen2 (`STANDARD_GEN_2`), владелец `ACCOUNTADMIN`. Gen2 — default для новых warehouse и на AWS стоит ×1.35 кредитов Gen1; `STATEMENT_TIMEOUT_IN_SECONDS` по умолчанию — 2 суток. → `setup.sql` создаёт проектный warehouse с явным `GENERATION = '1'`, `AUTO_SUSPEND = 60`, таймаутом 600 с и применяет те же лимиты простоя и таймаута к созданным заранее warehouse.
18. **Операции с метаданными не будят warehouse; `updated_on` — не журнал изменений.** `USE`, `SHOW`, `CREATE`/`DROP TABLE` и context-функции выполнялись при suspended `CRYPTO_WH` (`resumed_on` остался на последнем реальном запросе). `updated_on` менялся при холостом `ALTER ... SET` с теми же значениями и при каждом пробуждении. → Считать кредиты по метрингу warehouse, а не по числу запросов; дрейф конфигурации отслеживать сравнением свойств с `setup.sql`, а не по `updated_on`.
19. **Trial выдаёт роль PUBLIC, то есть всем пользователям.** При создании аккаунта `SNOWFLAKE_LEARNING_ROLE` выдаётся роли `PUBLIC`: `USAGE`/`OPERATE` на `SNOWFLAKE_LEARNING_WH` (Gen2, не под дневным монитором проектного warehouse) и `CREATE SCHEMA` в `SNOWFLAKE_LEARNING_DB`. Service-пользователь `CRYPTO_LOADER`, которому выдана только проектная роль, всё равно мог ей пользоваться: `SHOW GRANTS TO USER` показывал одну роль, а `CURRENT_AVAILABLE_ROLES()` в smoke-проверке вернул три. → Проверять эффективные роли, а не прямые гранты. `setup.sql` выдаёт роль админу и отзывает у `PUBLIC`; добавить её в ожидаемые роли значило бы узаконить утечку.
20. **Неверный пароль от ключа выглядит как отказ сервера.** Когда в `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE` по ошибке оказался публичный ключ, коннектор 5.2.0 выдал `250001 (08001): Failed to login: Authentication failed. Unspecified`, но в `LOGIN_HISTORY_BY_USER` попытки нет (следующий, успешный вход записан с `RSA_KEYPAIR`). Судя по всему, сбой был на клиенте (ключ не расшифровался), а сообщение говорит обратное. → При «Authentication failed» сначала смотреть журнал входов: записи нет — проблема на клиенте (пароль, файл ключа); запись есть — в ней `error_message` сервера.
21. **COPY пропускает уже загруженный файл, только пока тот не изменился, и сообщает об этом по каждому файлу.** Load metadata хранится по таблице 64 дня (имя файла, размер, ETag, число строк). `FORCE` описан как загрузка файлов «regardless of whether they were loaded previously and haven't changed», то есть изменённый файл с тем же именем загрузится снова. Повторный `COPY ... FILES = ('BTCUSDT.json.gz')` для загруженного файла вернул одну строку: `status = LOAD_SKIPPED`, `errors_seen = 1`, `first_error = "File was loaded before."`, таблица не изменилась. Сообщения «Copy executed with 0 files processed.» не было (2026-11-20). → Extract пишет неизменяемые каталоги батчей (`<batch_id>/<SYMBOL>.json`), файл под загруженным именем никогда не меняется; загрузчик считает `LOAD_SKIPPED` остановкой, решение принимает человек (`TRUNCATE` очищает load metadata, `FORCE` её игнорирует).
22. **PUT отвечает `SKIPPED` на другой файл с уже существующим именем и оставляет старый.** При `OVERWRITE = FALSE`, коннектор 5.2.0: PUT нового файла → `UPLOADED`; тот же файл ещё раз → `SKIPPED`; файл с тем же именем и новым содержимым → тоже `SKIPPED`, `message` пустой, а `LIST` показывает прежние размер и MD5 (эксперимент в отдельном каталоге stage, 2026-11-20). По ответу PUT эти два случая не различить. → Каталог батча никогда не перезаписывается (extract падает, если каталог есть). Известное ограничение: если загруженный в stage батч поправить локально (вместе с манифестом) и перезапустить, COPY загрузит старую версию из stage; сверка поймает это, только если изменилось число строк. Сравнить MD5 локального и staged-файла нельзя: gzip у разных компрессоров даёт разные байты (время в заголовке, настройки).
23. **Метаданные файла в COPY: относительный путь, MD5, номер элемента.** `METADATA$FILENAME` — путь внутри stage (`20261120T194005Z/BTCUSDT.json.gz`), а `LIST` и результат COPY добавляют имя stage (`klines_stage/20261120T194005Z/...`). `METADATA$FILE_CONTENT_KEY` совпадает с MD5, который `LIST` показывает для файла в stage (сжатого). При `STRIP_OUTER_ARRAY = TRUE` `METADATA$FILE_ROW_NUMBER` — позиция элемента массива с 1, в порядке файла (1..8759, `LAG` по нему не находит нарушений порядка). → Разбирать путь с конца (`SPLIT_PART(..., -1)`), а не по фиксированному префиксу; `_file_content_key` указывает точную версию файла, из которой пришла строка.
24. **Вывод `TIMESTAMP_LTZ` следует поясу сессии, а он по умолчанию — тихоокеанское время США.** `COPY_HISTORY.LAST_LOAD_TIME` и `created_on` в выводе `SHOW` пришли с `-0800`, что соответствует поясу сессии по умолчанию `America/Los_Angeles`. → Хранимые метки времени конвертируются явно: `_loaded_at = CONVERT_TIMEZONE('UTC', METADATA$START_SCAN_TIME)` (2-аргументная форма возвращает `TIMESTAMP_TZ`), и RAW читается одинаково из любой сессии (п. 4).
25. **JSON-строки остаются строками в `VARIANT`.** Binance шлёт цены JSON-строками; в RAW `TYPEOF(payload[1])` = `VARCHAR`, а `payload[1]::NUMBER(38, 8)` даёт точное десятичное число (`"86921.27000000"` → `86921.27000000`), `open_time` — `INTEGER`. → Цены приводить к `NUMBER(38, 8)` в staging, никогда через `FLOAT`/`TO_DOUBLE` (п. 3).
29. **Какие запросы шли на warehouse, показывает `WAREHOUSE_SIZE` в `QUERY_HISTORY`, а не `WAREHOUSE_NAME`.** У `CRYPTO_LOADER` (`INFORMATION_SCHEMA.QUERY_HISTORY_BY_USER`, 2026-11-20) у всех операторов `WAREHOUSE_NAME = CRYPTO_WH` (текущий warehouse сессии), но `WAREHOUSE_SIZE` заполнен только у `SELECT DISTINCT _batch_id`, `SELECT` статистики батча и `COPY`. У DDL (`CREATE ... IF NOT EXISTS`, `ALTER ... SET`), `PUT` и `SELECT` из context-функций в smoke-проверке он пуст. Холостой запуск загрузчика выполнил один оператор на warehouse (`SELECT DISTINCT`, 180 мс); он пришёл через 18 с после предыдущего запуска и застал warehouse работающим. Первый `SELECT DISTINCT` предыдущего запуска занял 720 мс. → Подтверждает п. 18 для `PUT` и DDL. Холостой запуск загрузчика стоит одного resume (минимум 60 с X-Small), если не попадает в окно `AUTO_SUSPEND` после другой работы; сделать его бесплатным — только не запускать (оркестрация или метка в stage, читаемая через `LIST`).
40. **Кэш результатов запросов сделал холостые запуски загрузчика бесплатными.** Четыре запуска `load_raw` за минуту (2026-11-21 11:56 UTC) — четыре сессии с 11, 3, 0 и 0 операторами на warehouse (`WAREHOUSE_SIZE` заполнен). Полная модель для первого запуска — 12 (3 lookup + 3 × статистика батча, `COPY`, статистика): его lookup свечей `SELECT DISTINCT _batch_id FROM RAW.BINANCE_SPOT_KLINES_1H` совпал по тексту с запуском прошлого дня, а таблица с тех пор не менялась, и Snowflake ответил из кэша результатов без warehouse. Второй запуск повторил все три lookup после того, как `COPY` первого изменил таблицы, — все три пошли на warehouse; третий и четвёртый застали таблицы неизменными и на warehouse ничего не выполнили. Картина 11 / 3 / 0 / 0 в точности совпадает с правилами кэша (тот же текст, таблица с тех пор не менялась). → Холостой запуск ничего не стоит, если с прошлого такого же lookup ничего не грузили; resume оплачивается только сразу после загрузки. Уточняет п. 29, где холостой запуск через 18 с после загрузки использовал warehouse; общим ответом остаётся пропуск холостых запусков оркестрацией (неделя 4).
